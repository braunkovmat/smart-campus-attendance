# ADR-0009: Разделение поля StudentName на FirstName и LastName

- **Статус:** принято
- **Дата:** 2026-10-29
- **Задача:** CAMPUS-103
- **Сервис:** attendance-service (учёт посещаемости пар)

## Контекст

В таблице `attendance_records` имя студента хранится одной строкой в поле `student_name` в формате «Фамилия Имя». Из-за этого нельзя сортировать и группировать по фамилии, а сопоставление со студентами из других сервисов кампуса даёт ошибки.

Сервис работает во время пар, его нельзя останавливать. Кроме того, с ним работают старые клиенты (мобильное приложение преподавателя, интеграция с деканатом), которые обновляются не одновременно.

## Рассмотренные варианты

1. **Одна миграция:** добавить колонки, перенести данные и удалить `student_name` в одном скрипте. Просто, но старые версии сервиса сразу ломаются, а `ALTER TABLE` может заблокировать таблицу. Нужен простой.
2. **Expand and Contract (в три фазы).** Сначала добавляем, потом переносим, в конце удаляем. Сложнее, зато без простоя.
3. **Триггер в БД,** который сам синхронизирует поля. Логика прячется в БД, её трудно тестировать и поддерживать.

## Решение

Выбран вариант 2, **Expand and Contract**:

1. **Expand** (`01_expand.sql`): добавляем `first_name` и `last_name` (допускают NULL). Сервис v1.9.0 пишет сразу в старое и в новые поля (двойная запись).
2. **Migrate** (`02_migrate.sql`): пачками по 1000 строк переносим старые данные.
3. **Contract** (`03_contract.sql`): когда все клиенты перешли, делаем новые поля обязательными и удаляем `student_name`.

Правило разделения старых значений: первое слово это фамилия, всё остальное это имя.

## Последствия

**Плюсы**
- Нет простоя, старые клиенты продолжают работать.
- Откат возможен на любом шаге (`kubectl rollout undo`), данные не теряются.
- Каждая фаза маленькая и проверяется отдельно.

**Минусы**
- Три релиза вместо одного, временно в БД лежат дублирующиеся данные.
- Код двойной записи нужно не забыть удалить после фазы Contract.
- Имена из нескольких слов делятся по простому правилу, возможны единичные неточности (проверяются запросом `mismatched`).

**Что делаем потом.** Через неделю после релиза отдельным CR выполняем `03_contract.sql` и убираем поле `StudentName` и код двойной записи из сервиса (релиз v2.0.0 с пометкой Breaking Change).
